# TeachUA — Docker + балансування навантаження (nginx)

Ця гілка(`nginx`) запускає вебдодаток TeachUA у контейнерах за допомогою Docker Compose та додає **nginx як балансувальник навантаження** перед двома екземплярами backend.

TeachUA — це проєкт, що складається з бекенду на Java, фронтенду на React та бази даних MariaDB/MySQL.

Підтримуються два режими розгортання:

| Режим | Compose-файл | База даних |
|---|---|---|
| Зовнішня БД | `docker-compose.external-db.yml` | Окремий сервер (наприклад, ВМ з Oracle Linux 10) |
| Локальна БД | `docker-compose.local-db.yml` | Контейнер MariaDB на тому ж хості |

Усі налаштування обох режимів зберігаються в одному файлі `.env`.

---

## Архітектура

```
 Браузер
    │
    ├──► frontend :3000   (React dev-сервер)
    │
    └──► nginx :8080  ──► backend1 :8080 ─┐
                     └──► backend2 :8080 ─┼──► MariaDB
                                          ┘     ├─ зовнішня БД: окрема ВМ, порт 3306
                                                └─ локальна БД: контейнер "db"
```

- Браузер звертається до backend **напряму через nginx**, тому `APP_HOST` має бути адресою, доступною з браузера (не внутрішнім іменем Docker).
- `backend1` і `backend2` не публікують портів назовні, вони доступні лише через nginx.
- Frontend не балансується

## Структура репозиторію

```
.
├── teachua-backend/
│   ├── Dockerfile                    # багатоетапна збірка: Maven (JDK 17) -> JRE 17, не root
│   └── data.sql                      # схема й початкові дані
├── teachua-frontend/
│   ├── Dockerfile                    # Node 16, запускає `npm start`
├── nginx/
│   └── nginx.conf                    # конфігурація балансувальника
├── docker-compose.external-db.yml    # nginx + 2 backend + frontend, БД на іншому сервері
├── docker-compose.local-db.yml       # nginx + 2 backend + frontend + контейнер MariaDB
├── .env.example                      # шаблон змінних середовища
└── README.md
```

## Вимоги

- Docker Engine з Docker Compose v2 (`docker compose version`)
- Щонайменше 4 ГБ ОЗУ (тепер працюють два JVM, а також збірка Maven і dev-сервер React)
- Вільні порти: `3000` (frontend) та `8080` (nginx)
- Для режиму зовнішньої БД: доступний сервер MariaDB/MySQL з порожньою базою `teachua` та користувачем, якому дозволено підключення з цього хоста

## Налаштування

```bash
cp .env.example .env
nano .env
```

Файл `.env` ігнорується git. **Ніколи не коміть його.**

| Змінна | Опис | Режим |
|---|---|---|
| `DB_HOST` | Адреса сервера бази даних | зовнішня БД |
| `DB_PORT` | Порт БД (за замовчуванням `3306`) | зовнішня БД |
| `DB_NAME` | Назва бази (за замовчуванням `teachua`) | обидва |
| `DB_USER` | Користувач БД | обидва |
| `DB_PASSWORD` | Пароль користувача БД | обидва |
| `DB_ROOT_PASSWORD` | Пароль root для MariaDB | локальна БД |
| `JDBC_DRIVER` | Клас JDBC-драйвера (`org.mariadb.jdbc.Driver`) | обидва |
| `BACKEND_PORT` | Порт, який публікує **nginx** (за замовчуванням `8080`) | обидва |
| `APP_HOST` | IP або імʼя цього хоста, яке бачить браузер | обидва |
| `FRONTEND_PORT` | Опублікований порт frontend (за замовчуванням `3000`) | обидва |
| `IMAGE_TAG` | Тег зібраних образів (за замовчуванням `local`) | обидва |

У режимі local-db бекенд завжди підключається до хоста `db` (контейнера бази даних), тому `DB_HOST` там ігнорується. Той самий файл `.env` працює для обох режимів.

## Запуск

### Режим 1: база даних на іншому сервері

Підготуйте базу даних один раз на сервері баз даних:

```sql
CREATE DATABASE teachua;
CREATE USER 'teachua'@'%' IDENTIFIED BY 'password';
GRANT ALL PRIVILEGES ON teachua.\* TO 'teachua'@'%';
FLUSH PRIVILEGES;
```
На сервері з базою даних імпортувати базу даних з репозиторію 
```bash
mariadb -u teachua -p teachua < data.sql
```
Потім на сервері з проєктом можна запустити команду
```bash

docker compose -f docker-compose.external-db.yml up -d --build
```

### Режим 2: БД у контейнері

```bash
docker compose -f docker-compose.local-db.yml up -d --build
```

Файл `data.sql` імпортується автоматично під час першого запуску (коли том `dbdata` порожній).

Не запускайте обидва режими одночасно: вони використовують однакові порти та назву проєкту. Зупиніть один перед запуском іншого.

## Перевірка

```bash
docker compose -f <compose-файл> ps
```

Усі сервіси мають бути у стані `healthy` (backend стартує до хвилини). Перший запуск фронтенду займає кілька хвилин. Дочекайтеся повідомлення `Compiled successfully` у виводі:

```bash
docker compose -f <compose-file> logs -f frontend
```

Потім відкрий `http://<APP_HOST>:3000`.

## Балансування навантаження

### Обраний алгоритм: `least_conn`

Запит надсилається на сервер з найменшою кількістю активних зʼєднань. Для REST API, де запити мають різну тривалість, це краще за просте чергування: завантаженіший сервер отримує менше нових запитів.

| Директива | Поведінка | Коли застосовувати |
|---|---|---|
| (без директиви) | round-robin, по черзі | однакові сервери та однакові запити |
| `least_conn` | найменше активних зʼєднань | **запити різної тривалості (обрано)** |
| `ip_hash` | один клієнт (за IP) завжди на один сервер | сесія зберігається в памʼяті сервера |
| `hash $request_uri consistent` | один URL завжди на один сервер | кешування |
| `random two least_conn` | 2 випадкові сервери, з них менш завантажений | багато серверів |

### Експерименти

**Відмовостійкість:**

```bash
docker compose -f <compose-файл> stop backend1     # сайт має працювати
docker compose -f <compose-файл> start backend1    # сервер повернеться за ≤10 с
```

**Зміна алгоритму або опцій** без зупинки сервісу:

```bash
# відредагуй nginx/nginx.conf, потім:
docker compose -f <compose-файл> exec nginx nginx -t          # перевірка синтаксису
docker compose -f <compose-файл> exec nginx nginx -s reload   # застосування
```

## Корисні команди

```bash
docker compose -f <compose-файл> logs -f nginx        # перегляд логів бекенду в реальному часі балансувальника
docker compose -f <compose-файл> logs -f backend1     # перегляд логів бекенду в реальному часі одного backend
docker compose -f <compose-файл> restart backend2     # перезапуск одного сервісу
docker compose -f <compose-file> up -d --build        # перезбірка та застосування змін
docker compose -f <compose-file> down                 # зупинка та видалення контейнерів
docker compose -f <compose-file> down -v              # також видалити том бази даних (local-db)
```

## Нотатки щодо реалізації

- **Образ бекенду.** Багатоетапна збірка (multi-stage build): WAR збирається за допомогою Maven на JDK 17 і запускається на базі JRE 17 від імені непривілейованого користувача (UID 10001). Налаштування бази даних передаються через змінні `DATASOURCE_URL`, `DATASOURCE_USER`, `DATASOURCE_PASSWORD` та `JDBC_DRIVER`.і
- **Два backend.** `backend1` і `backend2` описані одним шаблоном (`x-backend`) і збираються з одного образу.
- **nginx.** Образ `nginx:1.27-alpine`, конфігурація монтується з `nginx/nginx.conf` лише для читання. Запускається після того, як обидва backend стали `healthy`: nginx перетворює імена на IP при старті, і без цього завершився б з помилкою `host not found in upstream`.
- **Повторні спроби.** Якщо сервер не відповів або повернув 502/503/504, nginx повторює запит на іншому сервері. Запити POST/PUT/DELETE за замовчуванням не повторюються.
- **Образ фронтенду.** Запускає сервер розробки React (`npm start`), так само як додаток запускався без контейнерів. Це налаштування для розробки; у майбутньому планується збірка для production, що обслуговується через nginx.
- **Ініціалізація бази даних.** У режимі local-db `data.sql` виконується лише один раз. Щоб виконати повторний імпорт, перестворіть том.
- **Секрети.** Усі облікові дані беруться з `.env`. У git відстежується лише `.env.example`.
